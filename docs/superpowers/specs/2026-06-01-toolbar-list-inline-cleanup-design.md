# 编辑器工具栏：选中列表一键转横排逗号分隔设计

- 日期：2026-06-01
- 目标模块：`src/components/markdown-editor/Toolbar/*`、`src/components/markdown-editor/code/*`
- 状态：待评审

## 1. 背景

当前编辑器工具栏已经有“代码清理”下拉工具，适合承载一类“对当前内容做批量整理/转换”的动作。

本次需要在该区域新增一个工具：当用户选中列表内容时，可一键将列表转换为单行普通段落，并使用中文逗号 `，` 连接各列表项。分隔符本期先硬编码，后续再替换为可配置来源。

## 2. 用户目标

用户希望：

1. 在编辑器工具栏中，继续沿用现有“代码清理”工具入口。
2. 新增一个一键动作，把当前选中的列表转成横排文本。
3. 分隔符使用中文逗号 `，`。
4. 当前先硬编码，不做设置项。
5. 尽量保留列表项内部的行内格式（如加粗、链接、行内代码等）。
6. 多层嵌套列表直接拍平，按出现顺序输出，不保留层级结构。
7. 转换后替换为普通段落，而不是保留列表结构。

## 3. 范围

### 3.1 本期包含

- 在桌面工具栏现有清理下拉中新增一个菜单动作。
- 支持以下列表节点的转换：
  - 无序列表
  - 有序列表
  - 任务列表
- 将命中的列表内容替换为普通段落。
- 列表项之间插入中文逗号文本节点 `，`。
- 保留列表项中的行内 marks 与 inline 节点。
- 增加对应单元测试与工具栏接线测试。

### 3.2 本期不包含

- 不新增用户设置项。
- 不新增移动端单独入口（默认沿用桌面清理入口即可；若移动端未来也复用同一菜单数据，则由现有共享数据自然带上）。
- 不保留嵌套层级关系。
- 不处理非列表结构到横排文本的泛化转换。
- 不引入完整 registry 重构。

## 4. 方案比较

### 方案 A：直接把列表转换逻辑写进 `DesktopToolbar.tsx`

优点：改动少，落地快。

缺点：
- UI 文件继续膨胀。
- 行为逻辑难以单测。
- 后续替换分隔符或扩展更多清理动作时耦合更高。

### 方案 B：保留现有代码块清理文件，新增通用清理动作分发层，并把列表转换做成独立函数（推荐）

优点：
- 贴合现有“工具栏 -> 清理动作”的组织方式。
- 列表转换逻辑可独立测试。
- 未来把 `，` 换成配置项时改动局部。
- 不把“列表处理”混进“代码块清理”文件里。

缺点：比方案 A 多一层封装。

### 方案 C：把所有清理动作重构成完整注册表/策略系统

优点：扩展性最好。

缺点：对当前需求明显过度设计，风险与改动范围都偏大。

### 推荐

采用 **方案 B**。

## 5. 设计细节

### 5.1 入口设计

在现有“代码清理”下拉菜单中新增一项，例如：

- `列表转横排（中文逗号）`

该动作与现有清理项行为一致：
- 可直接点击执行。
- 可作为当前默认清理动作被记住（沿用现有 split dropdown 行为）。

## 5.2 数据与代码结构

### 保持不变

- `src/components/markdown-editor/code/codeBlockCleanup.ts`
  - 仍只负责代码块清理。

### 新增建议

- `src/components/markdown-editor/code/listInlineCleanup.ts`
  - 放置“选中列表转横排”的核心转换逻辑。
- `src/components/markdown-editor/code/editorCleanup.ts`
  - 统一分发编辑器清理动作。

### 调整文件

- `src/components/markdown-editor/Toolbar/data.ts`
  - 扩展清理菜单项数据。
- `src/components/markdown-editor/Toolbar/DesktopToolbar.tsx`
  - 从直接调用 `cleanupCodeBlocks(...)` 改为调用统一 cleanup dispatcher。
- 对应测试文件
  - 为新列表转换逻辑增加单元测试。
  - 调整工具栏源码接线测试。

## 5.3 动作模型

新增统一动作类型，覆盖：

- 现有代码块清理动作
- 新增列表横排转换动作

建议形态：

- `EditorCleanupActionKey`
  - 包含全部可从该菜单触发的动作 key
- Dispatcher 根据 key：
  - 命中代码块动作 -> 转发给 `cleanupCodeBlocks`
  - 命中列表动作 -> 调用 `convertSelectedListsToInlineParagraph`

这样不会污染代码块清理模块的领域边界。

## 5.4 列表转换行为

### 输入前提

- 基于当前 editor selection 处理。
- 只转换与当前选区相交的列表。

### 支持节点

- `bulletList`
- `orderedList`
- `taskList`
- 对应内部 `listItem` / `taskItem`

### 输出形式

- 将命中的列表整体替换成一个普通 `paragraph` 节点。
- 列表项之间插入文本分隔符 `，`。

### 核心规则

1. **拍平嵌套**
   - 所有层级的列表项按文档出现顺序展开。
   - 不在输出中保留层级、序号或 checkbox 状态。

2. **保留行内格式**
   - 列表项中的行内 marks 和 inline 节点保留。
   - 例如粗体、斜体、链接、行内代码继续存在。

3. **列表项内部多块内容的处理**
   - 同一列表项内如果存在多个文本/段落块，合并为同一项内容。
   - 块与块之间先插入普通空格 ` `，再继续拼接。

4. **列表项之间的连接**
   - 使用中文逗号 `，`。
   - 本期硬编码为常量，集中在单一位置定义，便于后续替换。

5. **空项处理**
   - 若某个列表项提取后没有有效 inline 内容，则跳过该项。
   - 如果所有项都为空，则不执行替换。

6. **无命中列表时**
   - 返回 unchanged 结果。
   - 工具栏提示“选区中没有可转换的列表”或等价文案。

## 5.5 可能的实现思路

建议在 `listInlineCleanup.ts` 中：

1. 从 selection 范围内找到最外层且命中的列表节点。
2. 对每个命中的列表：
   - 深度遍历其下所有列表项。
   - 抽取每个项中的 inline 内容。
   - 生成新的 paragraph content：
     - item1 inline content
     - `，`
     - item2 inline content
     - ...
3. 用事务替换原列表节点。
4. 从后往前替换，避免位置漂移。

### 关于“保留行内格式”的约束

为了保留 marks，不能只抽纯文本；应尽量复用原始 inline child 节点（或 clone 后复用其 JSON / ProseMirror 节点结构）。

### 关于 paragraph 合法性

生成的新内容必须满足 paragraph 的 schema 限制，只保留 inline 允许的子节点；遇到非 inline 块级节点时，递归提取其内部 inline 内容，而不是直接塞入 paragraph。

## 5.6 返回结果

建议复用与 `cleanupCodeBlocks` 相同的返回结构：

- `changed: boolean`
- `affectedCount: number`

其中：
- `affectedCount` 表示被成功转换的列表数量，而不是列表项数量。

这样工具栏提示逻辑可复用既有模式。

## 5.7 工具栏提示文案

新增动作后，应补对应成功/未变化提示：

- 成功：`已将 X 个列表转为横排文本`
- 未变化：`选区中没有可转换的列表`

文案可在实现阶段再与现有提示风格统一。

## 6. 测试设计

### 6.1 行为测试

建议新增/覆盖以下用例：

1. **无序列表转横排**
   - 输入：三个 bullet item
   - 输出：一个 paragraph，内容按 `项1，项2，项3`

2. **有序列表转横排**
   - 验证 ordered list 同样被转换

3. **任务列表转横排**
   - 不保留 checkbox，仅保留文本内容

4. **嵌套列表拍平**
   - 验证父项、子项按文档顺序展开

5. **保留行内格式**
   - 验证 bold / link / code 等 marks 未丢失

6. **同一列表项内多段内容合并**
   - 验证块之间插入空格

7. **无命中列表时 no-op**
   - 返回 `{ changed: false, affectedCount: 0 }`

8. **多个列表同时命中**
   - 验证 affectedCount 为列表个数，且事务替换顺序正确

### 6.2 工具栏接线测试

调整 `DesktopToolbar.source.test.ts`，检查：

- 新菜单 key 存在
- 工具栏不再只直接依赖 `cleanupCodeBlocks(tiptap, action)`
- 新 dispatcher 被调用
- 新提示逻辑接入

## 7. 错误处理

1. editor 为空：
   - 返回 unchanged
2. selection 无列表：
   - 返回 unchanged
3. 某些列表项无法提取 inline 内容：
   - 跳过该项，不中断整个动作
4. 替换结果为空：
   - 返回 unchanged

## 8. 对现有系统的影响

### 8.1 正向影响

- 扩展了工具栏清理能力。
- 为后续增加更多非代码块“整理动作”建立了更合理的结构。

### 8.2 风险

- 列表节点与选区相交判定若处理不当，可能会误改未选中的列表。
- 保留 inline marks 时，如果节点抽取不规范，可能触发 schema 不合法。
- 多列表替换时若不倒序处理，可能发生位置漂移。

### 8.3 风险控制

- 所有替换目标统一先收集、后倒序替换。
- 测试覆盖嵌套与多列表场景。
- 仅提取允许进入 paragraph 的 inline 内容。

## 9. 验收标准

满足以下条件视为完成：

1. 工具栏“代码清理”菜单中出现新动作。
2. 选中无序/有序/任务列表后可一键转为普通段落。
3. 列表项之间使用中文逗号 `，` 连接。
4. 嵌套列表按出现顺序拍平。
5. 行内加粗、链接、行内代码等格式保留。
6. 无列表时不报错，且给出未变化反馈。
7. 单元测试通过。
8. lint / test 通过。

## 10. 后续演进

后续可以在不推翻本设计的前提下扩展：

1. 把分隔符 `，` 改为配置项或多个预设。
2. 支持“转顿号分隔”“转分号分隔”“转句号分隔”。
3. 支持是否保留有序列表序号。
4. 支持是否把任务列表状态导出为文本前缀。

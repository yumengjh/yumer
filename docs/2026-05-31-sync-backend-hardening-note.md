# 2026-05-31 同步孤儿块问题的后端增强补充说明

## 背景

上一提交 `fix(sync): 修复空文档首块同步和孤儿块` 主要修复前端同步链路：

- 空文档首块无 `blockId` 时不再误判为已同步；
- create ack 返回后只 patch 同步 attrs，并写回 editor / React content / sync snapshot；
- 递归修正嵌套节点与顶层节点重复 `clientId`；
- 对 create ack 中已经不在本地 snapshot 的 clientId 自动补发 delete，清理同步语义上的孤儿块。

本补充文档用于明确：这类问题是否需要后端强制增强，以及已有 GC 能覆盖哪些范围。

## 两类“孤儿块”的区别

### 1. 数据库引用层孤儿块

这类块没有有效文档引用，或父子关系已经断开，例如：

- 块记录存在，但不再属于任何文档树；
- 父块不存在；
- 文档 root 不可达；
- GC 图遍历无法从文档入口抵达该块。

这类属于数据引用完整性问题。当前后端 GC 已经能够识别无文档引用的块，并在统一评估后继续清理，因此本轮前端同步修复不要求后端为此额外改动。

### 2. 同步语义层孤儿块

本轮 bug 中出现的“多余块”属于这一类：

1. 前端发出 create；
2. 用户在 create inflight 期间继续编辑或删除，使该 `clientId` 从当前本地 snapshot 中消失；
3. 服务端仍正常创建块，并把它挂在文档 root 下；
4. 该块在数据库引用关系上是有效的；
5. 但从用户当前本地文档语义看，它已经不应该存在。

这种块仍然在文档树中，仍有文档引用，GC 不应把它当成无引用孤儿块直接清理。否则 GC 会越权解释用户编辑语义，存在误删风险。

## 为什么本轮不需要后端必须增强

本轮根因发生在前端同步时序补偿缺失：

- 服务端收到 create 请求并成功创建块，是符合协议预期的；
- 前端在收到 create ack 时，才知道服务端实际创建了哪个 `blockId`；
- 如果此时本地 snapshot 已没有该 `clientId`，前端最清楚用户语义是“这个块已经被删除”；
- 因此前端应补发 delete，而不是让后端或 GC 猜测。

当前修复已经在前端 ack 处理层完成闭环：

- create ack 返回；
- 对比 ack mappings 与当前本地 snapshot；
- 若 ack clientId 不存在于本地 snapshot；
- enqueue 后续 delete 删除服务端刚创建的块。

所以从职责边界看：

- **前端同步层**：负责把用户当前文档语义同步到服务端；
- **后端 batch API**：负责幂等、排序、创建、更新、删除的可靠执行；
- **后端 GC**：负责数据引用层异常清理，而不是解释用户编辑语义。

## 后端已有 GC 的价值

后端 GC 仍然是必要兜底，主要覆盖：

- 请求失败或异常中断造成的无引用块；
- 历史版本迁移遗留的断链块；
- 非正常删除流程留下的不可达数据；
- 后续可能出现的服务端数据结构异常。

但它不应替代同步协议中的 delete 补偿，因为同步语义孤儿块在图结构上通常是可达的。

## 可选后端增强建议

以下增强不是本轮必须项，但可以提升可观测性和长期稳定性。

### 1. 增加短时间 create-delete 统计

后端可记录同一文档、同一 `clientBatchId` 或相近时间窗口内：

- create 后很快 delete 的数量；
- delete 对应的 create batch；
- create ack 到 delete 的时间间隔。

用途：

- 观察前端高频编辑下的同步抖动；
- 判断是否有异常大量 orphaned create 补偿；
- 为后续优化 debounce / batch 策略提供数据。

### 2. 保持 batch response 的 ack 字段稳定

前端补偿逻辑依赖 create ack 中的：

- `clientId`
- `blockId`
- `sortKey`
- `operation`
- `success`

建议后端继续保证这些字段稳定返回。尤其是 create 成功时，`clientId` 与 `blockId` 对前端补偿 delete 至关重要。

### 3. GC 报告区分孤儿类型

GC 报告可继续区分：

- 无文档引用块；
- 父子断链块；
- 逻辑删除块；
- 长期异常但仍可达的块。

注意：最后一类“仍可达但异常”的块只应报告或进入人工/规则评估，不应简单等同于可清理孤儿块。

### 4. 提供调试查询能力

可选提供按以下字段查询近期写入记录的调试能力：

- `docId`
- `clientBatchId`
- `syncCreateId`
- `clientId`
- `blockId`

用途：

- 快速定位某个多余块来自哪次 create；
- 关联前端 sync.log 与后端写入记录；
- 辅助判断问题在前端补偿、网络重试还是后端幂等层。

## 不建议的后端行为

不建议后端 GC 自动删除“仍挂在文档树上但前端本地没有”的块，因为后端通常没有当前编辑器本地 snapshot 的权威视角。

也不建议后端在 create ack 阶段主动推断该块是否已经被用户删除。删除语义应由后续 delete 请求表达。

## 结论

本轮 bug 的必须修复点在前端同步 ack 补偿层，后端没有必须同步修改。

后端现有 GC 对“无文档引用孤儿块”的清理仍然有价值，但它不能覆盖、也不应接管“仍在文档树中但用户已删除”的同步语义孤儿块。

后续后端可以优先做可观测性增强，而不是改变清理策略：

- 统计 create-delete 抖动；
- 稳定 batch ack 字段；
- 扩展 GC 报告分类；
- 提供按同步身份查询的调试接口。

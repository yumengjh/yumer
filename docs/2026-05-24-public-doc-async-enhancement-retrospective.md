# 2026-05-24 公开文档页异步增强与异常兜底改造复盘

## 1. 文档定位

这是一份面向项目维护者与后续开发者的复盘文档，用于总结 2026-05-24 这轮公开文档内容展示页优化的背景、实现过程、问题修正与最终结果。

本次改动主要覆盖以下几个方向：

- 公开文档页代码块渲染链路调整
- 页面加载完成事件（`load`）与异步增强解耦
- 设置（settings）请求延后到页面加载完成后执行
- 自定义 404 页面与错误页面补齐
- 代码块占位体验的回退与微调

这份文档既是阶段复盘，也可作为后续继续优化公开阅读链路时的上下文资料。

---

## 2. 背景与问题来源

### 2.1 页面已经能打开，但体验上仍有明显问题

在前一轮公开文档 SSR / 客户端代码块渲染方案落地后，页面基础能力已经具备：

- 服务端负责输出正文 HTML
- 代码块由客户端高亮器接管
- 页面支持公开访问、标签、作者、目录等基础信息展示

但从实际体验看，仍然存在三个不够理想的问题：

1. **代码块客户端渲染仍然容易落在首屏关键路径附近**
2. **文档展示页的 settings 请求会较早发起，可能干扰页面加载完成时机**
3. **404 / 错误兜底页面不足，rewrite 场景下表现不完整**

### 2.2 具体触发本轮改动的用户诉求

这次改动直接来自以下体验诉求：

- 代码块在未完成客户端渲染前，不要影响页面加载完成事件
- settings 请求也不要影响加载完成事件，应放到异步阶段处理
- 公开页需要自定义 404 页面与错误页面，并且错误页面应显示错误信息
- 代码块未渲染时的占位表现要尽量克制，不要干扰阅读

从目标上看，这轮改动不是要改变公开文档页的主架构，而是要把“首屏内容展示”和“后续渐进增强”切得更清楚。

---

## 3. 这轮改造的总体目标

本轮改造最终确定了 4 个目标：

1. **将代码块高亮明确放到页面加载完成后的异步阶段执行**
2. **将公开页 settings 拉取同样延后到页面加载完成后再执行**
3. **补齐公开页的 404 / error 兜底能力**
4. **让未渲染代码块保持低打扰、低高度占位，不提前暴露代码正文**

---

## 4. 最终方案总览

### 4.1 代码块渲染策略

最终保留的策略是：

- 服务端仍然只输出代码块 placeholder
- 代码块真正的高亮 HTML 仍由客户端生成
- 客户端渲染器不再紧贴首屏执行，而是延后到 `window.load` 后再进入空闲执行阶段

这意味着：

- 代码块不会阻塞页面的 `load`
- 页面能更早完成“可阅读正文”的加载阶段
- 高亮逻辑退居到增强层，而不是页面主加载链路

### 4.2 settings 请求策略

公开页展示设置（宽度、字号等）不再在组件初始阶段立即请求，而是：

- 页面先按默认设置渲染
- 等待 `window.load`
- 再通过 `requestIdleCallback`（若可用）或 `setTimeout` 进入异步拉取
- 成功后再覆盖展示变量

这样做的好处是：

- 首屏样式有默认值兜底
- settings 请求不会拖慢页面加载完成时机
- 公开阅读优先级高于个性化增强

### 4.3 404 / error 兜底策略

这轮补齐了两个层次的兜底页面：

- 全局 `app/not-found.tsx`
- 文档详情路由段 `app/doc/[slug]/not-found.tsx`
- 全局 `app/error.tsx`

其中最关键的一点是：

> `/blog/:slug` 实际会 rewrite 到 `/doc/:slug`，因此仅有全局 `not-found.tsx` 并不足以覆盖所有文档详情场景，必须补齐 `app/doc/[slug]/not-found.tsx` 才能稳定接住该路由段内的 `notFound()`。

### 4.4 代码块占位体验最终取舍

本轮中间曾尝试过“显示一条代码块渲染提示文案”的方案，但最终回退。

最终保留的体验策略是：

- 未渲染完成前，代码块内部**不显示任何提示文案**
- 也**不显示原始代码正文**
- 仅保留一个更矮的空占位框，减少布局跳动
- placeholder 最小高度由 `80px` 调整为 `48px`

这个方案更克制，也更接近用户对公开阅读页“安静加载”的预期。

## 5. 关键实现细节

### 5.1 关键文件

本轮主要涉及：

- `app/doc/[slug]/page.tsx`
- `src/components/DeferredCodeBlockRenderer.tsx`
- `src/components/ClientCodeBlockRenderer.tsx`
- `src/components/DocPageLayout.tsx`
- `src/services/generate-block-html.ts`
- `src/components/markdown-editor/styles/editor.css`
- `app/not-found.tsx`
- `app/doc/[slug]/not-found.tsx`
- `app/error.tsx`
- `src/services/__tests__/doc-page-ssr-rendering.test.ts`

### 5.2 `app/doc/[slug]/page.tsx`

这里的改动重点不是页面结构本身，而是把代码块客户端增强进一步“后移”。

原先页面直接挂载：

- `ClientCodeBlockRenderer`

现在改为挂载：

- `DeferredCodeBlockRenderer`

它本质上是一个 `dynamic(..., { ssr: false })` 的薄包装层，用来显式表达：

- 代码块客户端增强不是 SSR 的一部分
- 这段能力应当完全属于浏览器端异步增强逻辑

### 5.3 `DeferredCodeBlockRenderer`

新增文件：

- `src/components/DeferredCodeBlockRenderer.tsx`

职责非常单一：

- 通过 `next/dynamic` 延迟引入真正的 `ClientCodeBlockRenderer`
- 明确关闭 SSR

这样做的收益是：

- 页面源码语义更清晰
- 测试可以直接验证“确实使用了 `ssr: false` 的延迟加载包装”
- 后续如果还要进一步切换加载策略，也只需要改这一层

### 5.4 `ClientCodeBlockRenderer`

这里是本轮改动的核心之一。

原先逻辑可以理解为：

- 组件挂载后立即扫描 placeholder
- 立即初始化高亮器
- 立即逐块渲染

现在改成：

1. 等待 `window.load`
2. 再进入 `requestIdleCallback`（如果浏览器支持）
3. 否则退化到 `setTimeout(..., 0)`
4. 最后再开始高亮渲染

同时补充了两个行为：

- 代码块渲染失败时 `console.log("[public-doc] code block render failed", error)`
- 仅在块真正处理完成后才标记 `data-code-block-rendered="true"`

这样可以避免：

- 未完成渲染时提前把 placeholder 标记成已完成
- 渲染时序和页面加载完成阶段耦合过紧

### 5.5 `generate-block-html.ts`

这里负责服务端生成公开页代码块 placeholder。

本轮最终定稿后的行为是：

- placeholder 保留必要的 `data-*` 信息
- 保留 `data-code-block-code` 供客户端读取
- 但服务端输出的 placeholder 内部不直接显示代码
- 也不显示“渲染中”文案

这保证了两点：

1. 客户端仍有足够的数据完成高亮
2. 服务端首屏不会提前露出原始代码内容

### 5.6 `DocPageLayout.tsx`

这里负责公开页的展示设置异步增强。

新的行为链路是：

1. 页面先用默认 reader settings 渲染
2. 监听 `window.load`
3. 在 load 之后进入空闲回调或 `setTimeout`
4. 异步执行 `getClientVisibleSettings(workspaceId)`
5. 成功后覆盖展示变量
6. 失败时 `console.log("[public-doc] settings request failed", error)`，并回退到默认设置

这个改动的重点不是“settings 最终值更准确”，而是“不要拿它去抢页面主加载时机”。

### 5.7 `not-found` 与 `error`

本轮新增了三个兜底文件：

- `app/not-found.tsx`
- `app/doc/[slug]/not-found.tsx`
- `app/error.tsx`

其中：

- `app/not-found.tsx` 负责全局 404 样式兜底
- `app/doc/[slug]/not-found.tsx` 负责文档详情段内 `notFound()` 的定制落地
- `app/error.tsx` 负责显示 `error.message`，并在客户端打印 `console.log(error)` 供线上排查

## 6. 过程中的一次设计回退

### 6.1 为什么出现回退

本轮中间曾经尝试在代码块 placeholder 中加入：

- 标题 / 语言
- “代码高亮渲染中...” 文案

这样做的出发点是：

- 用户能知道这里不是空白 bug，而是在等待异步增强

但实际效果并不好，原因主要有两个：

1. **视觉噪音偏大**：公开阅读页强调正文流畅，提示文案会打断阅读节奏
2. **用户真实需求更克制**：用户更希望“先别显示，等渲染好了再整体出现”

### 6.2 最终决定

因此最终方案回退为：

- 不显示提示文字
- 不显示原始代码
- 仅保留一个较矮的空占位框

这是一次典型的“技术上可解释，不等于体验上更好”的调整。

## 7. 404 问题的真实根因

这轮里还有一个值得记录的问题：

用户访问类似：

- `http://localhost:3001/blog/mpjwyvxd-16fba3f12`

原本预期应该看到自定义 404，但实际没有进入预期页面。

排查后发现根因并不是：

- `notFound()` 没有执行

真正的关键在于：

- `/blog/:slug` 会先经由 `next.config.ts` rewrite 到 `/doc/:slug`
- 文档详情页实际命中的 App Router 段是 `/doc/[slug]`
- 因此这个 404 场景更依赖该段自身的 `not-found.tsx`

也就是说：

- 只有 `app/not-found.tsx` 不够
- 必须补 `app/doc/[slug]/not-found.tsx`

这也是为什么后续加上段级 not-found 后，问题链路才真正闭合。

## 8. 测试与验证

### 8.1 已补充的测试方向

本轮更新了：

- `src/services/__tests__/doc-page-ssr-rendering.test.ts`

主要增加了以下断言：

1. 页面通过 `DeferredCodeBlockRenderer` 使用客户端高亮增强

3. 未渲染的代码块 placeholder 不直接输出代码正文
4. `DocPageLayout` 会在 `window.load` 后再发起 settings 拉取

### 8.2 本地验证阻塞

这里需要特别记录一个现实问题：

本轮尝试执行以下验证时，仓库当前依赖环境存在异常：

- `pnpm exec vitest run ...`

出现过的典型报错包括：

- 找不到 `vitest.mjs`
- 找不到 `eslint.js`

因此，本轮在提交前能完成的是：

- 源码级静态检查
- 测试文件更新
- 路由链路与改动逻辑审查

而不能在当前环境中给出“测试全部通过 / build 通过”的结论。

这属于当前工作区依赖状态问题，不是本轮业务改动本身的直接报错，但仍应在复盘里明确记录。

## 9. 本轮改动的收益

本轮改造完成后，公开文档页的收益主要体现在以下几个方面：

### 9.1 首屏职责更单纯

页面加载完成前，重点只剩下：

- 基本文字内容可见
- 页面结构稳定
- 主要阅读链路成立

代码块高亮和 settings 请求都被后移到了增强阶段。

### 9.2 渐进增强边界更清晰

现在公开阅读页可以明显分成两层：

- **基础阅读层**：SSR HTML、标题、正文、元信息
- **增强层**：代码高亮、用户 / 空间展示设置覆盖

这有利于后续继续做性能优化，也更符合渐进增强原则。

### 9.3 异常兜底更完整

404 和错误页不再只停留在“有一个全局兜底”，而是考虑了：

- rewrite 后的真实路由段
- 线上错误信息可见与控制台日志可追踪

这对排查线上公开页问题是有帮助的。

### 9.4 代码块占位体验更克制

从产品体验上看，当前方案更符合阅读页气质：

- 没有提示噪音
- 没有原始代码闪现
- 只有更低高度的轻量占位

## 10. 已知不足与后续建议

### 10.1 当前仍未做到按视口懒渲染代码块

现在代码块是：

- `load` 后异步执行
- 但仍会一次性扫描并处理页面上的全部 placeholder

后续如果文档很长、代码块很多，可以考虑继续优化为：

- 进入视口后再高亮
- 或者优先渲染首屏附近代码块，后续分批处理

### 10.2 settings 拉取仍可能带来一次样式覆盖跳变

当前已经把请求后移，但若用户 / 空间设置和默认值差异较大，仍可能在 load 后出现一次宽度或字号变化。

后续可考虑：

- 将公开可见的 reader settings 做更轻量的服务端透传
- 或使用更稳定的初始缓存策略

### 10.3 验证环境需要单独修复

当前工作区的依赖解析异常，会影响：

- 自动化测试可信度
- lint / build 验证闭环
- 提交前的工程把关效率

建议后续尽快单独处理一轮依赖环境修复。

## 11. 结论

这轮改动没有推翻公开文档页的整体方案，而是完成了一次很重要的“职责收口”：

- 首屏负责尽快把正文展示出来
- 代码块高亮和 settings 覆盖退居异步增强阶段
- 404 / 错误兜底从“有”提升到了“链路完整”
- 代码块占位策略也从“可解释”调整成了“更克制”

如果用一句话总结，这轮改动的核心价值是：

> 让公开文档页更像一个稳定、安静、以阅读为先的页面，而不是把所有增强逻辑都塞进首屏加载过程里。

# 2026-05-25 公开文档统一快照缓存补丁复盘

## 1. 文档定位

这是一份针对 2026-05-25 这轮公开文档页补丁改造的复盘文档，重点记录以下内容：

- 为什么上一轮公开文档缓存改造还不够彻底
- 这次为什么要把首屏服务端数据进一步收敛为统一快照缓存单元
- `/latest` 路径为什么要彻底旁路缓存
- 为什么主动失效从单纯 `revalidatePath` 升级为 `tag + path` 双保险
- 这次实施过程中踩到的 Next 16 / TypeScript / Server Component 兼容问题

这篇文档是对上一份主复盘文档 `docs/2026-05-24-public-doc-cache-retrospective.md` 的补充，不重复描述上一轮的总体缓存策略，而是聚焦这次补丁级演进。

---

## 2. 背景：上一轮缓存方案为什么还不够

上一轮改造已经完成了几件关键事情：

- `/blog/:slug` 默认缓存
- `/blog/:slug/latest` 强制 `no-store`
- 公开文档内容接口默认切到 `mode=html`
- 发布后通过前端 revalidate API 主动刷新对应路径

从大的方向看，这已经把公开文档页从“每次请求都实时打后端”推进到了“更接近 ISR / 近 SSG 的公开页”。

但用户在实际使用中又发现了一个新的瓶颈：

> 页面正文虽然已经缓存了，但首屏返回过程中仍然可能被文档元数据、标签元数据等附加请求拖慢，导致整体响应没有真正达到预期。

这说明上一轮虽然已经引入缓存，但缓存粒度仍然偏“分散”：

- 正文请求有缓存
- 元数据请求也有缓存策略
- 标签请求也有缓存策略
- `generateMetadata()` 还会单独走一遍取数逻辑

这些逻辑虽然都能缓存，但它们还没有形成真正意义上的“统一首屏缓存单元”。

---

## 3. 这次改造真正要解决的问题

这次补丁的目标不是重新设计公开文档页面，而是更进一步收敛缓存边界：

### 3.1 把首屏服务端数据收敛成一个统一快照

需要统一缓存的不只是正文 HTML，还包括一切会影响首屏直接返回的服务端数据，例如：

- 文档正文渲染结果
- 文档标题、图标、分类、作者、更新时间、浏览量
- 标签 ID 到标签名称 / 颜色的解析结果
- 页面和 metadata 都依赖的标题等字段

### 3.2 让 `generateMetadata()` 不再走单独慢链路

如果页面本体和 metadata 各自维护一套取数逻辑，即便两边都有缓存，仍然容易出现：

- 两套逻辑各自演进
- 首屏链路分散
- 调试时难以判断究竟是谁拖慢了返回

因此，这次明确要求：

> 页面本体和 `generateMetadata()` 必须复用同一个公开文档快照读取入口。

### 3.3 明确 `/latest` 不是“刷新缓存”，而是“纯实时旁路”

这次对 `/latest` 的语义也做了进一步收紧：

- 不读取正式缓存
- 不回写正式缓存
- 只作为验收、排障、实时对照入口

这样可以避免调试路径意外污染线上默认缓存。

### 3.4 主动失效不只按路径，而要按文档对象整体失效

既然这次的缓存对象已经从“页面路径上的若干散落请求”收敛成“公开文档快照单元”，那么失效语义也应该升级为：

- 这篇公开文档整体失效
- 而不只是“把 `/doc/:slug` 这条路径重算一下”

因此这次引入了缓存 tag，并保留路径失效作为双保险。

## 4. 最终方案总览

### 4.1 引入统一快照服务 `public-doc-snapshot`

新增：

- `src/services/public-doc-snapshot.ts`

它承担了公开文档首屏服务端数据聚合层的职责，统一完成：

1. 解析 slug
2. 获取正文内容
3. 获取文档元数据
4. 解析标签元数据
5. 读取后端渲染诊断响应头
6. 生成最终可用于页面和 metadata 的快照对象

### 4.2 页面与 metadata 统一从快照读取

`app/doc/[slug]/page.tsx` 不再各自维护：

- `getDocMetadata()`
- `getDocContent()`

而是统一使用：

```ts
getPublicDocSnapshot(slug, latest)
```

这样做之后：

- `generateMetadata()` 和页面本体共享同一份服务端数据入口
- 首屏取数链路更清晰
- 缓存边界真正变成“公开文档快照”

### 4.3 默认公开页命中缓存，`/latest` 彻底旁路

这次在 `public-doc-snapshot.ts` 中明确区分了两类分支：

#### 默认公开页

- 使用 `unstable_cache`
- 统一设置 `revalidate`
- 统一挂到文档级缓存 tag

#### `/latest`

- 使用 `cache: "no-store"`
- 直接实时读取后端
- 不进入默认快照缓存单元

### 4.4 失效策略升级为 `tag + path`

之前前端的 revalidate API 只做：

```ts
revalidatePath(`/doc/${slug}`)
```

这次升级为：

```ts
revalidateTag(getPublicDocCacheTag(slug), "max")
revalidatePath(`/doc/${slug}`)
```

其中：

- `tag` 负责从“文档对象”语义上失效统一快照缓存
- `path` 作为现有页面路径失效补充，避免遗漏

这让失效语义更完整，也更适合后续继续往“统一缓存对象”方向演进。

## 5. 关键实现细节

### 5.1 新增 `getPublicDocCacheTag()`

统一使用：

```ts
public-doc:${slug}
```

作为这篇公开文档的缓存标签。

它的意义是：

- 一篇文档对应一个稳定的缓存标识
- 页面、metadata、正文、标签解析等服务端首屏数据都围绕这一个标识组织

### 5.2 引入 `resolvePublicFetchOptions()`

为了避免默认缓存分支和 `/latest` 分支在各处重复判断，这次新增了统一 fetch 参数分发：

- 默认页：`revalidate + tags`
- `/latest`：`cache: "no-store"`

这样做一方面减少重复，另一方面也让“是否进入正式缓存单元”这个决策集中到一个地方。

### 5.3 快照仍然保留标签请求失败可降级

虽然这次把标签元数据也纳入统一快照，但没有改变原有的错误语义：

- 正文或文档主元数据失败：返回 `null`，页面 `notFound()` 或无法渲染
- 标签请求失败：忽略标签信息，页面仍可展示

这说明“统一快照”并不意味着所有字段都必须硬依赖成功，而是：

> 在一个统一读取入口里保留不同字段原本的业务优先级。

### 5.4 客户端延后增强逻辑保持不动

这次补丁有一个明确边界：

- **只收敛服务端首屏数据**
- **不动客户端 load 之后异步增强的 settings 请求**

也就是说：

- `DocPageLayout.tsx` 里页面加载完成后再异步请求 settings 的策略仍然保留
- 代码块客户端高亮延后增强的策略仍然保留

这能保证这次改动聚焦在“服务端首屏缓存边界”本身，而不把客户端增强逻辑重新搅乱。

## 6. 实施过程中踩到的真实问题

这次改动虽然目标明确，但在真正落地时暴露出几个工程层面的兼容问题。

### 6.1 `next/dynamic({ ssr: false })` 不能直接放在 Server Component 里

在第一次重构 `app/doc/[slug]/page.tsx` 时，曾直接在页面文件中写了：

```ts
dynamic(() => import(...), { ssr: false })
```

但 `app/doc/[slug]/page.tsx` 是 Server Component，这在 App Router 中不允许。

最终修复方式是恢复项目原本更稳妥的模式：

- 页面里只引用 `DeferredCodeBlockRenderer`
- `DeferredCodeBlockRenderer` 作为 Client Component
- `ssr: false` 的动态加载逻辑只放在这个客户端包装层中

这个问题本质上与快照缓存无关，但它是在这次改造过程中被真实触发的构建问题，因此需要在复盘里记录。

### 6.2 Next 16 的 `revalidateTag` 类型签名变化

这次引入 `revalidateTag` 后，第一次构建报错：

- 当前项目使用的 Next 16 类型要求 `revalidateTag` 接收两个参数

因此最终修成：

```ts
revalidateTag(getPublicDocCacheTag(slug), "max")
```

这不是业务设计问题，而是具体版本下的 API / 类型签名约束。

### 6.3 `requestIdleCallback` 分支触发 TypeScript 收窄异常

在两个客户端组件里都出现了类似错误：

- `Property 'setTimeout' does not exist on type 'never'`

涉及文件：

- `src/components/ClientCodeBlockRenderer.tsx`
- `src/components/DocPageLayout.tsx`

最终修法不是改功能，而是改成更稳定的类型写法：

- 用 `typeof window.requestIdleCallback === "function"` 判定
- fallback 里改用 `globalThis.setTimeout(...)`

这属于 TypeScript / DOM 类型系统在当前版本下的兼容性细节。

### 6.4 `RequestInit` 三元表达式类型宽化

在 `public-doc-snapshot.ts` 中，最初写法类似：

```ts
latest ? { cache: "no-store" } : publicFetchOptions(slug)
```

结果 `cache: "no-store"` 被推宽成普通 `string`，不再满足 `RequestInit` 需要的 `RequestCache` 字面量类型。

最终通过新增 `resolvePublicFetchOptions()` 并显式收口返回类型解决。

## 7. 这次补丁带来的收益

### 7.1 首屏服务端缓存边界真正收敛

现在默认公开文档页的首屏服务端数据不再是“正文一块、metadata 一块、标签解析一块”，而是统一进入一个聚合读取入口。

这让缓存设计更符合直觉：

> 一次公开文档首屏返回，对应一份公开文档快照。

### 7.2 metadata 与页面主体不再各走各的

这次统一之后，标题等 metadata 不再独立维护单独取数路径。

收益包括：

- 首屏行为更一致
- 逻辑更少分叉
- 后续排障时只需要盯住一个服务端聚合入口

### 7.3 `/latest` 语义更纯粹

以前可以把 `/latest` 理解成“强制实时读取”；现在进一步明确成：

- 只读实时数据
- 不参与正式缓存
- 不承担刷新缓存职责

这让它真正成为一个干净的对照通道。

### 7.4 主动失效链路更符合“按文档对象刷新”

引入 tag 之后，失效不再只是“页面路径刷新”，而是开始具备：

- 这篇文档的公开快照整体失效

这样的语义基础。

这对以后继续扩展公开文档页首屏依赖项很重要。

## 9. 仍然存在的边界与后续建议

### 9.1 统一快照仍是前端聚合，不是后端聚合接口

这次补丁选择的是“前端服务端聚合层”，不是新建后端统一接口。

好处是：

- 变更面更小
- 能快速验证统一缓存边界

但代价是：

- 仍然存在多次后端 fetch，只是这些 fetch 已被聚合进同一个快照读取入口

如果后续还要继续压缩首屏复杂度，可以考虑是否需要后端提供单一公开页聚合接口。

### 9.2 当前仍保留 `tag + path` 双保险

这次保留了：

- `revalidateTag(...)`
- `revalidatePath(...)`

这是一种稳妥做法，但也说明路径失效还没有完全退出舞台。

后续如果验证 tag 语义已经足够稳定，可以再评估是否继续精简。

### 9.3 列表页缓存仍然是另一条线

这次补丁只处理文档详情页的统一快照缓存，不涉及：

- `/blog` 列表页的统一缓存方案

因此如果后续要继续推进“公开文档整体近 SSG 化”，列表页仍是单独需要处理的一段。

---

## 10. 总结

如果说上一轮改造解决的是：

> 公开文档页“有没有缓存、有没有主动刷新”的问题

那么这次补丁解决的则是：

> 首屏服务端缓存边界够不够收敛、`latest` 语义够不够纯粹、失效对象能不能真正围绕“这篇文档”来组织。

这次改动本身不大，但意义很明确：

- 默认公开页更接近真正的统一快照缓存
- metadata 与页面主体行为一致
- `/latest` 更像纯实时旁路
- 缓存失效链路开始从“按路径”走向“按文档对象”

从公开文档页长期演进的角度看，这次补丁不是推翻重来，而是把上一轮已经建立起来的缓存路线，真正往“可维护、可解释、可继续扩展”的方向再推进了一步。

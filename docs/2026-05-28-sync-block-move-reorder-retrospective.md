# 2026-05-28 块移动误带其他块重排复盘

## 1. 背景

在连续换行、空格、`create ack sortKey` 等同步问题修复后，手工回归显示内容同步已经稳定很多，但块拖拽仍然存在残留问题：

- 编辑器内拖动一个块时，视觉结果短时间内是正确的
- 刷新后顺序会漂移
- 网络日志里一次用户拖拽会发出多条 `move`

这说明问题已经不再是“块内容没有同步”，而是“顺序意图被错误编码后同步到了后端”。

本轮复盘聚焦的场景来自 `log/log.txt`：

```txt
初始顺序: 23456
拖拽后本地顺序: 62345
刷新后服务端回读顺序: 63452
```

---

## 2. 现象与日志证据

日志中这次拖拽对应的 `/blocks/batch` 请求不是一条 `move`，而是两条：

```json
[
  {
    "type": "move",
    "blockId": "b_1779931156743_96b7974e",
    "sortKey": "001437"
  },
  {
    "type": "move",
    "blockId": "b_1779931156737_b5a87fe4",
    "sortKey": "005938"
  }
]
```

这和真实用户意图不一致。用户只拖动了尾部块 `6` 到最前面，预期最多只需要：

- 给块 `6` 分配一个新的更小 `sortKey`
- 其余块保留原有相对顺序和原有排序键

因此，日志里的第二条 `move` 本身就是异常信号。后端返回成功只能说明它执行了客户端给出的排序意图，不能说明这份意图是对的。

---

## 3. 根因链路

### 3.1 问题不在后端执行层

后端当前 `move` 处理做的是：

1. 校验块和父节点是否合法
2. 为请求中的目标 `sortKey` 预留唯一值
3. 写入新版本

只要前端发来的 `move` 序列本身有漂移，后端就会忠实落库。也就是说：

- 后端没有凭空“多移动一个块”
- 根因是前端在 diff 阶段错误地产生了额外 `move`

### 3.2 旧算法直接拿“新位置邻居的旧 sortKey”做夹点

`deriveSyncEntries` 旧逻辑在给重排块计算新 `sortKey` 时，会：

1. 先看该块在“新顺序”中的前后邻居是谁
2. 直接读取这些邻居节点当前 attrs 上携带的旧 `sortKey`
3. 用这两个旧键值做 `createSortKeyBetween(...)`

这个策略对“插入新块”通常够用，但对“已有块整体重排”不成立。因为：

- 新顺序已经变了
- 邻居关系变了
- 但邻居身上的 `sortKey` 仍然代表旧顺序

一旦把尾部块拖到头部，就会出现“位置已经在前面，但排序键仍然很大”的节点。

### 3.3 为什么 `23456 -> 62345` 会多出第二个 move

以上述场景为例，原始排序键近似为：

```txt
2 -> 001750
3 -> 002750
4 -> 003750
5 -> 004750
6 -> 005750
```

拖成 `62345` 后：

- 对块 `6` 来说，新位置在最前面，算法会算出一个更小的键，例如 `000875`
- 这一步本身是对的

但继续处理块 `2` 时，旧逻辑会认为它前驱已经变成了“排在它前面的块 `6`”，于是拿：

```txt
previous = 005750
next = null 或后续块的旧键
```

再给块 `2` 计算一个新的更大排序键，于是额外生成第二条 `move`。这就把原本不该动的块也拖入了重排链。

后续块再基于这组漂移过的排序事实继续计算，刷新后顺序就会进一步偏离。

---

## 4. 修复思路

这次修复没有继续在“单个块当前位置如何取夹点”上打补丁，而是先做一层稳定排序规划：

### 4.1 先识别哪些已有块可以作为稳定锚点

对“下一帧文档中的已有块”提取它们在旧顺序中的排序值，计算最长递增子序列（LIS）：

- 仍然保持相对顺序不变的块，保留旧 `sortKey`
- 这些块作为稳定锚点

这一步的意义是把“真的被拖动的块”和“只是因为别的块插到前面而索引变化的块”区分开。

### 4.2 只为非锚点区间重新分配排序键

在锚点之间，把连续需要重排的块作为一个 run 统一分配 `sortKey`：

- 左边界取上一个已确定锚点的目标键
- 右边界取下一个稳定锚点的旧键
- 用 `createSortKeysBetween(...)` 一次性为整个 run 分配排序键

这样：

- 被拖到最前面的块 `6` 会拿到新的更小键
- 块 `2/3/4/5` 因为仍然保持相对顺序，会继续保留旧键
- 不会再凭空生成第二条 `move`

### 4.3 diff 判定改成“目标 sortKey 是否真的变化”

修复后不再依赖“索引变了就可能要 move”的局部判断，而是：

- 先规划每个已有块的目标 `sortKey`
- 只有目标键和旧键不同，才发出 `move`

这让 move 的生成基于排序事实，而不是基于临时索引变化。

## 7. 经验教训

### 7.1 “相邻块”不等于“有效排序锚点”

在重排场景里，屏幕上的相邻关系可以先变，但排序元数据还没变。直接用新相邻关系去读取旧排序键，本质上是在混用两个时间点的事实。

### 7.2 reorder 不能按单块局部贪心处理

插入场景可以局部算一个 `between`，但已有块重排往往是一个整体问题。先规划整段排序，再决定哪些块要 move，稳定性明显更高。

### 7.3 后端“执行成功”不代表同步意图正确

这次问题再次说明：

- 请求成功
- 数据成功落库
- 刷新前界面看起来也对

都不代表同步链路没问题。只要请求层已经带上了错误意图，后端越稳定执行，最终结果越稳定地错误。

---

## 8. 后续建议

1. 增加浏览器级拖拽 E2E，用真实拖拽覆盖“头尾互换、跨多块插入、连续拖拽再刷新”。
2. 如果后续支持更复杂的树形块移动，排序规划应扩展到父节点切换场景，而不是只看顶层 sibling。
3. 调试日志里可以继续输出“旧顺序 / 目标顺序 / 发出的 move 列表”，便于快速判断是 diff 生成错了，还是后端落库错了。

---

## 9. 总结

这次块移动残留问题的根因，不是后端 move 接口错误改动了其他块，而是前端用“新位置的邻居 + 旧排序键”混算目标顺序，导致一次真实拖拽被编码成多条 `move`。

修复的关键不在于再补一个特殊判断，而在于把“已有块重排”从局部夹点计算，提升为“先规划稳定目标排序，再按差异生成 move”。这样才能保证用户只移动一个块时，同步层也只表达这一个块的顺序变化。
